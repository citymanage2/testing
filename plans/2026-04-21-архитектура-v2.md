# План: Перестройка архитектуры функционала СМ Смета (v2)

**Дата:** 2026-04-21
**Статус плана:** в работе
**Стек:** не меняется (Python/FastAPI/SQLAlchemy async/PostgreSQL/Alembic/Anthropic SDK на бэке; React 18/TypeScript/Vite/Zustand на фронте).

---

## 1. Контекст и причина

Текущая архитектура MVP неудобна пользователям: порядок действий не совпадает с тем, как реально работают сметчик, менеджер проекта, снабженец и руководитель. Модули слабо связаны, данные разрознены, ИИ плохо встроен в сквозной поток работы. Задача — перестроить функциональную архитектуру под реальный рабочий процесс генподрядчика, не трогая стек.

## 2. Границы перестройки

**В скоупе:**
- Функциональная модель (сущности, модули, их связи, порядок действий).
- UX-потоки под ролей.
- Глубокая интеграция ИИ в работу со сметами и ведение проекта.

**Вне скоупа на этом этапе:**
- CRM и воронка продаж — остаются в Битрикс 24. Система стартует с момента создания проекта.
- Полевые сценарии (прораб/снабженец на объекте) — позже, через ТГ-бота или лёгкую версию.
- Внешние интеграции (1С бухгалтерия, банк, поставщики) — позже.
- Миграция данных из текущего MVP/Gectaro/Битрикс/Excel — чистый старт.

## 3. Архитектурное ядро

### 3.1. Центральная сущность
**Проект (объект строительства)** — корневая сущность. На проекте висит всё: сметы, ГПР, бюджет, материалы, документы, участники, финансы.

### 3.2. Роли пользователей
- **Сметчик** — главный пользователь сметного модуля, работает с ИИ-копилотом.
- **Менеджер проекта / прораб** — ведёт объект, ГПР, заявки на материалы, факт.
- **Руководитель / финансист** — смотрит П&У, дашборды, согласует сметы и закупки.
- **Менеджер по продажам** — согласует сметы и КП (без отдельной воронки в системе).
- **Снабженец** — закупки, склад, распределение материалов.

### 3.3. Роль ИИ
1. **Копилот сметчика** — парсит входы, нормализует позиции, предлагает аналоги, подтягивает источники цен (своя база, прайсы, ФСНБ), проверяет достоверность.
2. **Сквозной помощник проекта** — работает во всех модулях: смета → ГПР → заявки → факт → отчётность.

Принцип: никаких цифр «из воздуха», каждая позиция со ссылкой на источник цены.

## 4. Модули новой архитектуры

### 4.1. Сметный модуль (ядро первого этапа)

**ЦКП этапа:** быстро и достоверно превратить вход заказчика в нашу смету себестоимости генподрядчика, а затем в финальное КП с прибылью — отдельно по сметам и сводно по проекту.

**Входные данные, которые система должна принять и нормализовать:**
- Сметы заказчика (Excel, PDF).
- ТЗ и описания работ (текст, Word, PDF).
- Проектная документация (чертежи, PDF) — извлечение объёмов.

**Модель сметы:** одна смета с несколькими слоями цен на одну позицию:
- Цена заказчика.
- Себестоимость (наша).
- Цена субподряда.
- Факт (после исполнения).

**Состав себестоимости:**
- Материалы — по прайсам поставщиков, собственной базе, ФСНБ.
- Работы своих бригад — по внутренним расценкам.
- Работы субподряда — по ценам субов.
- Накладные — логистика, техника, офис (распределение коэффициентом).

**Версионирование:** ветки со статусами:
- Черновик → внутренняя → к заказчику → подписанная.
- Сравнение веток, выбор финальной версии, неизменяемость подписанной.

**Поведение ИИ-копилота:**
- Парсинг входов в унифицированную структуру.
- Сопоставление позиций входа с нашим каталогом работ/материалов.
- Предложение аналогов материалов.
- Подтягивание источников цен.
- Проверка достоверности (алерты на цифры без источника).

### 4.2. Управление проектом и ГПР
- ГПР собирается по проекту из всех смет проекта (не по одной смете).
- Позиции смет привязаны к этапам/работам ГПР для план/факта.
- Зависимости между этапами, критический путь.

### 4.3. Материалы и заявки
- Гибридная модель: центральный склад компании + объектные склады.
- Движения между складами, заявки с объекта, закупки снабженца.
- Списание — по фактическому использованию, связь с позициями смет.

### 4.4. Финансовая картина
- План/факт по проекту в реальном времени.
- П&У по проекту и по компании.
- Прогноз до конца проекта на основе текущего факта и остатка сметы.
- Денежные потоки (в перспективе, после интеграций).

## 5. Принципы архитектуры

1. **Достоверность важнее скорости** — каждая цифра с источником, технически обязательное поле.
2. **Надёжность — основа доверия** — один сбой = откат к Excel, стабильность не обсуждается.
3. **Всё в одном месте** — без переключения между программами.
4. **Проект-центричность** — все сущности привязаны к проекту.
5. **ИИ как часть потока, а не отдельный инструмент**.

#### ERD — модель данных v2

```
users
  id PK | username | hashed_password | role | email

projects
  id PK | name | description | address | client_name
  start_date | end_date | status | construction_type
  contract_number | contract_date | budget_planned | notes
  created_by FK→users | created_at | updated_at

project_members
  id PK | project_id FK→projects | user_id FK→users
  role ENUM(estimator|project_manager|director|sales_manager|supply_manager)
  created_at

price_sources
  id PK | company_id | name
  source_type ENUM(pricelist|fsnb|internal|manual)
  url | reference_date | created_at

catalog_items
  id PK | company_id | item_type ENUM(work|material)
  code | name | unit | description | category | subcategory
  is_active | created_at | updated_at

catalog_prices
  id PK | catalog_item_id FK→catalog_items | price_source_id FK→price_sources
  work_price NUMERIC | material_price NUMERIC
  effective_date | created_at

estimates                                   ← главная сущность «смета»
  id PK | project_id FK→projects
  name | description
  status ENUM(draft|internal|to_client|signed)
  is_locked BOOL                            ← True после подписания
  parent_id FK→estimates (self)             ← ветвление/версии
  version_name                              ← «v1», «Ред. 2», …
  estimate_type ENUM(client|subcontract)
  calculation_method ENUM(manual|ai)
  created_by FK→users | created_at | updated_at

estimate_sections
  id PK | estimate_id FK→estimates
  parent_id FK→estimate_sections (self)     ← вложенные разделы
  name | order_index | created_at

estimate_positions                          ← позиция сметы
  id PK | estimate_id FK→estimates
  section_id FK→estimate_sections (nullable)
  catalog_item_id FK→catalog_items (nullable)
  row_type ENUM(item|header|total)
  name | unit | quantity NUMERIC
  order_index | created_at | updated_at

price_layers                                ← 4 слоя цен на позицию
  id PK | position_id FK→estimate_positions
  layer_type ENUM(client|cost|subcontract|actual)
  work_price NUMERIC | material_price NUMERIC | total NUMERIC
  price_source_id FK→price_sources (nullable)
  notes
```

**Статусная машина сметы:**
`draft` → `internal` → `to_client` → `signed` (is_locked=True)
Откат: `signed` → `to_client` (разблокирует is_locked), `to_client` → `internal`, `internal` → `draft`

**Схема ролей:**
- `estimator` — создаёт/редактирует сметы
- `project_manager` — ведёт ГПР, материалы, факт
- `director` — полный просмотр + согласование
- `sales_manager` — просмотр КП, согласование
- `supply_manager` — закупки, склад
